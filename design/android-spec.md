# AudioFool Android — design spec

The Android version of AudioFool, for a Galaxy S24 Ultra (Android 17) and a FiiO M21 (Android 13). It keeps the desktop's two themes, PS1 Light and PS2 Dark, and the desktop's colours, unchanged.

This file is the source of truth for layout and behaviour. Numbers are in `mobile-tokens.json`; colours, shadows and radii are the desktop tokens in `theme-tokens.json` (Light) and `theme-tokens.dark.json` (Dark). The PNGs in `screens/` show every screen in both themes at both device sizes. If this spec and a PNG disagree, the spec wins. If the spec says nothing about something, ask.

## 1. Platform

- Kotlin and Jetpack Compose. `minSdk 33` (the M21), target the newest SDK installed.
- Portrait only. Draw edge to edge: the status and navigation bars sit over the window background, and content keeps clear of them with system insets. In the mockups the 28 dp row at the top and the 20 dp handle at the bottom stand in for the system bars; don't draw them.
- Navigation is a drill-down with **no on-screen back buttons**. The system back gesture goes up one level. Predictive back is on.
- Sideloaded, so the app uses **all-files access** (`MANAGE_EXTERNAL_STORAGE`) and stores plain folder paths.
- Music can be on internal storage, an SD card, or both, about 26,000 tracks. An SD card can be removed at any time. As on desktop, **an unreachable folder is never treated as a deleted library**: its tracks are kept, shown as unavailable, and return when the card does.
- Font: Selawik, bundled (see `mobile-tokens.json` → `font`). Numbers use tabular figures.

## 2. Theme

- PS2 Dark and PS1 Light, switched by hand, saved, and **Dark when nothing is saved**. The switch is in Settings and the logo menu. It applies at once, with nothing rebuilt or interrupted.
- Every colour comes from a token. Don't put hex values in screens.
- Both colour files are the desktop's, copied unchanged. A test checks they have the same keys, as the desktop parity test does.
- Mobile-only colours live in `mobile-tokens.json` → `color`. There is one so far: the BP label (§6.4).
- In Dark, the desktop's title-bar glow sits at the top of every screen: a radial gradient from `color.window.titleGlow`, shape `titleBar.glow.*` (900 × 130 at 50% / −40), fading at 45% (40% of the alpha) and clear at 75%. It's transparent in Light.

### Shared parts

- **Panel**: `color.panel.bg`, 1 dp `color.panel.border`, `radius.surface`, `shadow.panelHighlight`; inset `panel.marginX` each side and `panel.marginBottom` below. Header row `panel.headerHeight` with a 1 dp `color.panel.divider` under it; label uppercase, 600, letter-spaced, `color.text.muted`.
- **Rows**: `radius.row` corners. Selected: `color.state.selectionBg`, the second line turns `color.text.secondary`, a placeholder thumbnail's border turns `art.thumbBorderSelected`.
- **Covers** are drawn edge to edge with no border, everywhere (the user's call, 0.2.2: the 1 dp frame read as a light outline). Only the placeholder for an album without a cover keeps its 1 dp border (`art.border`, or `art.thumbBorder` in lists), so its square still shows. Now playing: `color.state.nowPlayingBg`, weight 600, text `accent.playbackText`.
- **Chip**: `settings.chipHeight`, `color.status.chipBg`, 1 dp `color.status.chipBorder`, `radius.chip`, text `color.text.status`.
- **Round buttons**: `color.control.face`, 1 dp `color.control.faceBorder`, `shadow.controlButton`. Play/Pause uses `shadow.playButton`, plus a 1 dp `color.control.playRing` ring and `shadow.playGlow` (both invisible in Light), with the icon in `accent.playback`. Both shadows are drawn without their bottom inset layer, the desktop's molded lip (`inset 0 -3px` / `-4px`), which on the phone read as a small fill (the user's call, 0.7.2): the top highlight and the drop shadow stay. This covers Now Playing's six buttons and the mini player's three; the token sheet still shows the desktop's tokens as they are. On Now Playing, Play/Pause's icon, ring and glow take the cover's colour and the glow shows only while playing (§5, Cover colour and Controls row); the mini player's keep the theme's and its glow. **While a finger is on a round button its face is `control.faceHover`** (2026-11-09, the user's call), the desktop's hover colour standing in for touch as `state.hoverOverlay` does on rows; this covers all nine. A button that can't be pressed (BP greyed, §6.4) doesn't show it. Each button has a name for a screen reader (Previous, Play or Pause, Next, Repeat, Shuffle, Bit-Perfect, with Repeat's, Shuffle's and Bit-Perfect's state), and Now Playing's seekbar is a slider it can read and move ("Seek").
- Album titles wrap to two lines, then "…". Everything else is one line with "…".
- No visible scrollbars. Lists scroll by touch. Artists' letter strip (§4.1) and Albums' year strip (§4.2) are the only things drawn at a list's edge (the user's calls, 0.2.0 and 0.11.0).
- A tap on a song plays it, with the rest of its album queued after it, and opens Now Playing on it (the user's call, 0.1.1). A tap on an artist or album opens it.

## 3. Mini player

On every library screen, under the panel. Shows the cover, title (600, `text.primary`), artist (600, `accent.blue`), and Previous, Play/Pause and Next. Sizes are in `miniPlayer.*`: skip buttons are 36 dp faces in 44 × 48 dp touch areas, and Play/Pause is a 44 dp face in a 48 dp touch area. A tap anywhere else opens Now Playing. Hidden until something has been played.

## 4. Library screens

### 4.1 Artists (the start screen)

- Top bar: the PlayStation logo (`PlayStation-Logo-1994.png`, unchanged, 36 × 28 in a 48 dp touch area), then the search field filling the rest. A tap on the field opens Search.
- **The logo is the menu button.** Its menu holds, in alphabetical order (the user's call, 0.7.1), Listening History (§4.7), Rescan Library, Settings, Statistics and Theme (switches at once), then the app's version ("Version 0.7.0"), information only like the cover menu's resolution (label `text.muted`, value `text.secondary`). Rescan Library (the user's call, 0.5.0: the same rescan as the refresh button in Settings' Music folders; the menu closes and the scan runs in the background). A rescan the user starts (here or in Settings) shows in the ARTISTS header's right side, in `text.muted` (0.7.0): "Checking for changes…", then "Reading tags: 120 of 400" if files changed, then for 4 s how it ended: "Up to date · 3 new, 1 updated, 2 removed" (only the counts that aren't zero; "no changes" when none; "· 1 folder unavailable" when a folder can't be reached). A note too long for the header ellipsizes; the label keeps its width. Automatic scans (at start, a card mounted) show only "Reading tags" while they read tags, as before.
- Panel "ARTISTS". Each row: a 48 dp thumbnail of the artist's **newest album** (latest release date, using the desktop's release-date rules), the name (16, `text.primary`) and the album count, e.g. "3 albums" (13, `text.muted`). The order follows the desktop (`ArtistOrder`).
- **Shuffle button** (0.9.0, the user's request; no mockup, not on the desktop): a small shuffle icon at the far right of the ARTISTS header, the same button as Settings' Music folders refresh (`settings.headerActionButton`, icon `settings.headerActionIcon` in `text.muted`). A tap plays the whole library shuffled from a random song: the queue is every song that can be reached (a removed SD card's are left out), in library order (artists, their albums, the albums' songs), and Shuffle is turned on, so the desktop's `PlayOrder` shuffles it as it does an album, with the random song first. Turning Shuffle off in Now Playing carries on in library order from the song playing; another tap reshuffles from a new random song. Now Playing opens on the song, as for a tapped song (the user's call); back returns to Artists. A rescan's note (below) sits left of the button and ellipsizes before it. No button while the library is empty. Now Playing's track count takes thousands separators ("12,345 / 27,115").
- **Letter strip** (the user's call, 0.2.0; no mockup, sizes in `artists.index.*`): a narrow pill at the list's right edge holding only the letters the library has, in list order. An artist files under the first letter of its sort key ("The Beatles" under B), accents dropped ("Åsa" under A); digits and symbols under "#", other scripts under "•". Always shown (0.2.1; 0.2.0 showed it only while the list scrolled); the rows end `width` + 2 × `marginEnd` from the list's edge so they never run under it. A touch or a slide along it jumps the list to that letter's first artist, with a haptic tick at each new letter, and a bubble in the middle of the list shows the letter (the logo menu's surface, the letter 36/600 in `text.heading`). The letters are `text.muted`, the current one `text.primary` at 600. Not shown, and no room kept for it, when the library has fewer than two letters.

### 4.2 Albums

- Top bar: the artist's name (18/600, `accent.blue`) over the album count (13, `text.muted`), and a search button on the right.
- Panel "ALBUMS". Each row: a 64 dp thumbnail, the title (16, two lines) and "1997 · 10 tracks" (13). The order follows the desktop's release-date sort.
- **Year strip** (the user's call, 0.11.0; no mockup): Artists' letter strip (§4.1), same pill, sizes (`artists.index.*`), touch, tick and bubble, holding the **years** the artist's albums came out in, in list order, since the list is by release date, not A–Z. Each year is written "’97"; the bubble shows "1997" (it widens past its square for four digits, `bubblePaddingX` either side). Albums with no year (at the list's foot) are under "?". **Shown only when the albums don't all fit** the list (rows are a fixed height, so it is known before drawing), and when they span two years or more; otherwise the rows keep the full width. When the years would sit closer than `minSlot` (sixty years on the M21), every few is written, each over its run's share of the strip, the current year in its run's place; a finger still picks each year, and the bubble names it.

### 4.3 Album

- Top bar: the artist's name (15, `text.muted`) and a search button.
- Panel header block: 72 dp art with `shadow.headerArt`, the title (21/600, `text.heading`, two lines), the artist (14/600, `accent.blue`) and "1997 · 10 tracks · 42:58" (13, `text.secondary`).
- Table header "# · SONG · TIME", then rows of `album.rowHeight`. The # column starts at the row's start, with the numbers (and "#") left-aligned; it is `album.columns.number.width` wide, or the album's longest number if wider. The song playing shows an 8 × 10 solid triangle in `accent.playback` in its number's place (2026-11-06; the mockups in `design/screens/` still show the earlier triangle slot left of a right-aligned number). Discs follow each other in order; there's no disc column.

### 4.4 Search

- Top bar: the field in its focused state (`state.searchFocusBg`, a 2 dp `state.searchFocusRing` ring), the query, and a clear (×) button. Results update as you type; the matching follows the desktop's `LibrarySearch`.
- Three groups, each with a panel header, shown only when they have results: **ARTISTS** (name and album count), **ALBUMS** (thumbnail, title, "Artist · 2003 · 11 tracks"), **SONGS** (title, "Artist · Album", time). The song playing gets the now-playing row style.

### 4.5 Settings

The screen title "Settings" (18/600) and four panels, `settings.sectionGap` apart:

- **Appearance**: Theme, showing "PS2 Dark" or "PS1 Light", with a chip holding a moon (Dark) or sun (Light) icon. A tap switches.
- **Playback**: Bit-Perfect, with the output readout (§6.3) under the label and a chip with a status dot (`status.bitPerfectOn` / `status.bitPerfectOff`, ring `status.dotRing`) and the word "Bit-Perfect". It's the same setting as the BP button (§6.4), greyed out in the same cases.
- **Music folders**: a refresh button in the header (rescans; the same note as the ARTISTS header, left of the button, 0.7.0). One row per folder, with a checkbox (filled `accent.playback`, check in `panel.bg`) to include or leave out, the folder's name ("SD card · Music") and its path. Then "Add Folder…", which opens a folder picker and saves the plain path.
- **Last.fm**: a dot and "Last.fm: not connected", with a Connect button. Once connected: "Last.fm: connected as <user>" with Disconnect. The dot is `status.lastFmDot` while scrobbling, `status.lastFmOff` otherwise; "Last.fm: connect again" when Last.fm rejects the session. Connect opens a form in the panel (after 0.8.0, the user's call): a line saying AudioFool keeps the session, never the password, then the Last.fm **Username** and **Password** fields (the password as dots; both offered to the phone's password manager; the name filled in when connecting again), Cancel and Connect, and "Signing in…" while it's sent. A refusal shows over the fields: "Last.fm didn't accept that username and password." Until 0.8.0 the form asked for the API key and shared secret and approved in the browser (session 5). A failed send adds the queue line under the status.

### 4.6 Statistics

There's no mockup. Build it from the same parts (panels, headers, rows, `type.statValue` for big numbers), and show the user a screenshot before finishing. It shows:

- **Library totals**: tracks, albums, artists, size on disk.
- **Formats**: tracks per format (FLAC, DSD, MP3, …), using the desktop's format names (`AudioFormats`).
- **Listening time**: total time listened, recorded by the app from now on.

As built (session 5, approved from screenshots): LIBRARY holds Tracks, Albums and Artists in one row and Play time and On disk in the next, as `type.statValue` figures with a label under each, then the scan line. FORMATS has one bar row per format (label; "count · share · size"; a `playbackBar.trackHeight` bar in `slider.volumeFill` on `slider.track`). LISTENING shows the time and "Listened since <date>". Then a DEBUG panel with one row, "Playback and debug numbers", which opens the **Debug** screen: the Playback and Debug panels (what the user reads off when reporting from a phone). They sat on Statistics itself until 0.2.2 (the user's call).

### 4.7 Listening History

The desktop's Listening History window (its session 74) as a screen (the user's request, 0.8.0; no mockup), from the logo menu and Now Playing's cover menu. What the user has played, as Last.fm has it: read-only, nothing saved. Built from Statistics' parts (panels, `type.statValue` figures, bar rows; sizes in `statistics.*` and `listeningHistory.*`) in one column, the desktop's left column then its right. The logic is the desktop's, ported with its tests (`ListeningJson`, `ListeningMatch`, `HistoryTime` for its `ListeningTime`, the reads in `LastFmApi`). From the top:

1. The title "Listening History · <user>" (just "Listening History" when not connected).
2. Panel **TOTALS**: Scrobbles and Scrobbling since ("Dec 2025") on one row, then Artists, Albums and Tracks; a count Last.fm leaves out drops its figure.
3. **The period switch**, for the three top lists: six short words in equal slots across the screen, **7D · 1M · 3M · 6M · 12M · All** (the user's call: the desktop's "7 Days … All Time" don't fit one row on either phone). As the desktop's: the chosen one `text.heading` at `dialog.emphasisWeight`, the rest `text.muted`; a touch target high (`listeningHistory.periodHeight`). Opens on 12M. Each period is fetched once per opening, so going back to one is instant; while one is fetched its three panels say "Loading…".
4. Panels **TOP ARTISTS**, **TOP ALBUMS**, **TOP TRACKS**: ten each, Statistics' bar rows: the name (15, `text.primary`), "866 plays" (13, `text.muted`), the bar measured against the first row (`slider.volumeFill`, never the playback colour), and under albums and tracks the artist (13, `text.muted`). A list with nothing in it says "Nothing played in the last 12 months." (the desktop's words).
5. Panel **RECENTLY PLAYED**: the last 20 plays, newest first, what is playing now at the top. No bar: the time ("Now playing", "12 min ago", "2 hours ago", "Yesterday", "Oct 30") where the plays go, "Artist · Album" under it.

**A tap on a row the library holds** goes to it, as the desktop's click (names matched loosely: case, accents, punctuation, "&" and a trailing "(Remastered)" don't matter): an artist opens its Albums screen, an album its Album screen, and a song **opens its album with the song chosen** (drawn selected and scrolled into view; the user's call, over playing it). Back returns to Listening History as it was, without asking Last.fm again. A row the library doesn't hold looks the same and does nothing.

It reads with the saved API key and user name only (unsigned GETs: no secret, no session). Each opening from a menu asks Last.fm afresh. Not connected: a LAST.FM panel says so, and a tap opens Settings. While loading: "Loading from Last.fm…". When it can't: "Couldn't load your listening history", the reason under it, and a tap tries again.

## 5. Now Playing

Opens from the mini player, and when a song is tapped (in a list or in Search). It has **no buttons at the top**: system back closes it, back to the screen underneath. There is no swipe down (the user's call, 0.2.0). **Swiping the art or the title block sideways skips**: left is Next, right is Previous (the button's rule: more than 3 s in, it restarts the song). They follow the finger and fade; let go past `nowPlaying.swipeSkipDistance`, or flick faster than `swipeSkipVelocity`, and the song changes with them back in place at once (no animation; 0.2.0's spring back after a skip left them stuck off the screen on the S24). Short of that, they spring back. The seekbar keeps its own sideways drag. From top to bottom:

1. **Art**, square, `nowPlaying.paddingX` from each side, `nowPlaying.artTop` below the status bar. Its side is the smaller of (screen width − 40) and (screen height − `artHeightReserve`), so on the M21 it shrinks to leave the controls room. The reserve is 366 dp since 0.2.2 (426 before): the one-line quality and the shorter controls row gave the M21's cover about 60 dp more (301 dp, from 241), with the title block lower (the user's call). The S24's cover is limited by the width, so it is unchanged. `shadow.headerArt`; no border round a cover (§2, Covers).
2. **Title** (22/600, `text.heading`), **artist** (16/600, in the cover's colour; `accent.blue` without one; Cover colour, below) and **album** (15, `text.secondary`), left-aligned. The **track count "3 / 10"** (15, `text.muted`) sits right of the title, aligned to its top. There's no Like button. **A tap on the artist's name opens that artist's albums; a tap on the album's name opens the album with the song chosen** (2026-11-09, the user's call), as a Listening History row does (§4.7), and back returns to Now Playing. The name pressed shows it, as a row does (`state.hoverOverlay`). Where the artist named isn't in the artists list (a guest on someone else's album), it is the artist the album is under. A song the library doesn't hold leads nowhere. A sideways drag across the names still skips.
3. Flexible space, weight 3. **Spare height** (0.2.3, the user's call): where the width limits the cover (the S24), the height it can't use, screen height − `artHeightReserve` − the cover's side (about 120 dp on the S24, none on the M21). The waveform takes `waveformGrowth.ofSpare` of it (up to `max`), and the space at 7 grows toward weight 3, level with it at `spareEvenAt` dp of spare, so the S24 has two even gaps instead of one over the quality line. With no spare (the M21) nothing changes.
4. **Quality**, one right-aligned line right above the seekbar (13, `text.secondary`): format, bitrate, bit depth, sample rate, "FLAC · 1,901 kbps · 24-Bit · 48 kHz" (the user's order, 0.2.2; two lines before). Lossy files have no bit depth ("MP3 · 320 kbps · 44.1 kHz"). DSD gives its rate in MHz: "DSD · 5,645 kbps · 1-Bit · 2.8 MHz" (DSD64). Anything not known is left out.
5. **Waveform seekbar**, full width, 40 dp (64 on the S24, from its spare height; see 3): the track's waveform as one filled shape mirrored about the middle, through 600 RMS levels (the desktop's `Waveform.Columns` and `WaveformView` outline; 0.2.4, the user's call from a reference picture: RMS only, both channels combined, no playhead line; 96 hard-edged bars before), played part in the cover's colour (Cover colour, below; `slider.seekFill` without one), the rest `slider.track`. The split falls at the exact place, through the bar being played, so it glides while playing (the desktop's `WaveformView`; 0.2.0, the user's report). Drag or tap to seek. **While a finger drags it, the time it would seek to shows in a bubble over the finger** (2026-11-09, the user's call; `nowPlaying.scrubBubble`): the index strips' bubble surface (§4.1), the time 22/600 in `text.heading`, centred over the finger and kept inside the bar's ends, its foot 36 dp above the bar so it clears the quality line and a thumb; it takes no room, and goes when the finger lifts. The elapsed time at the left shows the same time meanwhile, as before. Compute the waveform as the desktop's `Waveform` does, in the background, cached per file. Until it's ready, show a flat bar `waveformFloor` high.
6. **Elapsed** left, **total** right (13, `text.muted`).
7. Flexible space, weight 1 (up to 3 with spare height; see 3).
8. **Controls row**: on the left, three 34 dp round buttons: **Repeat** and **Shuffle** side by side, 8 dp apart, their tops level with Play/Pause's top, and **BP** centred under them, its bottom level with Play/Pause's bottom (the user's call, 0.2.2; a column of three before). On the right, for a right thumb, **Previous**, **Play/Pause** and **Next**, centred on Play/Pause. Their size follows the screen height (`nowPlaying.skipButton`, `playButton`, `transportGap`: a fraction of the screen height, between a min and max). That gives 70 / 96 / 22 dp on the S24 and about 57 / 78 / 17 dp on the M21. At least `modeToTransportGap` (12 dp) lies between the two groups; where that doesn't fit, the transport's gaps shrink (the S24: about 10 dp). With spare height (see 3) the row sits `controlsLift` above the readout (0.2.4, the user's call: the S24's buttons were too close to the bottom to press comfortably; 0.2.5 and 0.2.6: higher still): 0.46 of the spare, up to 56 dp, so 56 dp on the S24 (37 at font size 1.3) and none on the M21. 0.7.1 (the user's call: the S24's readout sat awkwardly close to the bottom), `readoutLift` of that gap (0.17 of the spare, up to 20 dp, never more than `controlsLift`) goes under the readout instead: the readout rises 20 dp on the S24 and the buttons stay where they were. None on the M21. **The glow round Play/Pause shows only while playing** (2026-11-09, the user's call): paused, the ring alone is left, so the glow says at a glance that music is playing (Dark; Light has no glow). The mini player's Play/Pause keeps its glow either way. The three 34 dp buttons need no larger box to be easy to hit: a touch up to 7 dp outside one still presses it, since Compose widens a small touch area to 48 dp by itself (`NowPlayingTouchTest` pins this).
9. **Output readout**, centred (13, `text.muted`), e.g. "Speaker · 48 kHz · Resampled" (§6.3).

Repeat: off `control.iconOff`; on, the cover's colour (`control.repeatOn` without one); repeat-one adds the desktop's "1" badge (`playbackBar.repeatOneBadge`), its disc in the same colour. Shuffle: off `control.iconOff`; on, the cover's colour (`control.shuffleOn` without one). Order and repeat follow the desktop's `PlayOrder`.

**Cover colour** (2026-11-09, the user's requests: first "the main color theme of the album art" as the accent, then the rest of this list from a set of mock-ups; no design mockup, and the phone's own: the desktop has no such rule). On Now Playing the cover's colour stands in for the theme's:

- the **seekbar's played part** and **Play/Pause's icon** (for `accent.playback`);
- the **ring and glow round Play/Pause**, each at its own token's opacity (`control.playRing`, `shadow.playGlow`). In Light, where the theme's ring is clear, the cover's colour still makes one (`nowPlaying.coverAccent.ring`: 2 dp at 0.67), so the colour shows round the button there too; Light has no glow, with or without a cover;
- **Repeat and Shuffle when on**, and Repeat One's badge (for `control.repeatOn` and `control.shuffleOn`), so the screen has one colour for "on". BP keeps its own two (§6.4): they say whether Bit-Perfect is on, not that something is lit;
- the **artist's name** (for `accent.blue`; the one place an artist's name isn't blue);
- the **glow at the top of the screen** (for `window.titleGlow`, at its opacity; Dark only, as the glow is).

Nothing else changes: the mini player, the now-playing rows, the other buttons and every other screen keep the theme's colours.

- **The cover's main colour** (`core/.../art/CoverColor.main`): the middle square of the cover, as the screen shows it, scaled down to 64 × 64. Pixels with too little colour say nothing (grey, black, white, off-white; a dark pixel needs less chroma to count than a light one, so a dark brown is brown and a cream is off-white). The rest are counted by hue, each by how colourful it is, and the hue with the most wins; the colour is the average of that hue's pixels. So a red logo on a black cover gives red, and a blue sky with a small sun gives blue. A cover less than 2% coloured (black and white), or no cover, has no colour: everything above keeps the theme's own.
- **Fitted to the theme** (`CoverColor.accent`, `AppTheme.coverAccent`): the same hue, at a lightness within `nowPlaying.coverAccent.lightnessRange` (0.15 of OKLab's 0 to 1) of the theme colour it stands in for, on the side away from the background: that or lighter on Dark, that or darker on Light. So it is never harder to see than the colour the theme was designed with. For everything but the artist's name that colour is `accent.playback`; the artist's name is text, so it is fitted to `accent.blue` and comes out lighter on Dark and darker on Light than the seekbar. Made lighter, the colour keeps its saturation (a deep red cover gives a red, not a greyish pink); made darker, its chroma (a pastel stays a colour). It is worked out from the theme as it is drawn, so a theme switch changes it at once.
- **The cover stays until the next one is read**, picture and colour: nothing blinks between an album's songs (up to 0.12.0 the art showed the empty placeholder for a moment at every song change), and both change when the new cover appears. A song with no cover shows the placeholder and the theme's colours once that is known.

**Cover menu** (0.6.0, the user's call; no mockup): a long press on the art (with a haptic tick) opens a menu at the finger, kept `artMenu.edgeMargin` inside the screen, in the logo menu's look (`menu.*`, `artMenu.width`). Its rows: **Resolution**, the cover's own pixel size, "1200 × 1200" as the desktop's art viewer writes it ("No cover" without one); information only, so it isn't tappable and its label is `text.muted`. Then **Analyze** (§5.1) and **Genius** (§5.2, the user's call). Then the logo menu's rows (0.7.4, the user's call), as there: Listening History (§4.7, 0.8.0), Rescan Library, Settings, Statistics, Theme (keeps the menu open), and the version last; so all but the resolution are in alphabetical order. Listening History, Settings and Statistics open over Now Playing, and back returns to it. A tap outside or system back closes it; so does the song changing. A sideways drag still skips: it takes the touch before the long press is due.

### 5.1 Analyze

The desktop's Analysis window (`AnalysisWindow`) as a screen, opened from the cover menu; system back returns to Now Playing, and leaving stops the analysis. The whole file is decoded in the background on its own stream (`TrackAnalyzer`, ported), beside playback; DSD is read as 176.4 kHz PCM. Nothing is written or cached. Sizes are in `mobile-tokens.json` → `analysis`; the colour scale, label spacings and cutoff marker are the desktop's `analysis.*` and `color.spectrogram.*` tokens. From the top:

1. The song's title (18/600, `text.heading`) over "Artist · Album · FLAC · 24-bit · 96 kHz · 6:14" (13, `text.muted`, two lines at most), the desktop's subtitle.
2. Panel **SPECTRUM**: the spectrogram (time left to right, frequency bottom to top, the six `spectrogram.level*` colours from `analysis.floorDb` to `analysis.topDb`), `analysis.picture` of the screen height, in a 1 dp `art.border` frame; frequencies on the left, the colour scale with its dB every `legendStepDb` on the right, times underneath (at least a second apart). The cutoff, when there is one, is a dashed `spectrogram.marker` line labelled at its right end. While reading: "Reading the file… 42%" over a bar in `status.scanTrack` / `status.scanFill`, on the panel's grey. A file that can't be read: the reason (600, `text.heading`) in its place.
3. AudioFool's opinion (`QualityOpinion`, ported with its wording and tests): the verdict as a headline (18/600, `text.primary`), each finding's reasons (15, `text.secondary`), then the figures "Cutoff 16.2 kHz · Peak −0.3 dB · 24 of 24 bits used" (13, `text.muted`; "Read as 176.4 kHz PCM" for DSD).

The page scrolls when the opinion is long. Not ported: the desktop's Quality Check clear buttons (the phone has no library-wide check). A removed SD card stops a read from it at once (§1).

### 5.2 Genius

The desktop's Genius window (its session 75) as a screen (the user's request; no mockup), opened from the cover menu's **Genius** row: what genius.com has on the song, comments included, but not the lyrics (Genius never hands them out). System back returns to Now Playing. The screen stays on the song it was opened for when the next one plays; opening it again from the menu looks the song up again (instantly when it was found before). Read-only; nothing is saved. The logic is the desktop's, ported with its tests (`core/.../genius/`: `GeniusClient`, `GeniusJson`, `GeniusMatch`, `GeniusLookup`). It reads genius.com's own web API (`genius.com/api/`, no key; the one its pages use, the only one with comments and questions), which is undocumented: a change on Genius's side shows as a failure here and nowhere else. Sizes are in `mobile-tokens.json` → `genius`, with the album header's (`album.*`) and Statistics' (`statistics.*`); no new colours. One column, titled "Genius", from the top:

1. **The library's song**, in a panel drawn as the Album screen's header (§4.3): its album's cover, the title, the artist (`accent.blue`) and "Album · Year" from its tags, then **Open on Genius** once a page is loaded, which opens the page in the browser (or Genius's app). The header stays the library's song when one of the nearest results is chosen; the page under it is Genius's.
2. Panel **GENIUS**, only when there is something to say (Listening History's way, §4.7): "Looking up on Genius…"; "Genius has no page that matches this song."; "This song has no title to look up on Genius."; "Genius's page for this song has nothing on it yet."; or, tappable with "Tap to try again." under it, "Couldn't load the Genius page." with the reason, and "Genius didn't send the comments this time." when only a part failed (the desktop says to open the song again instead).
3. Panel **CLOSEST ON GENIUS**, with no match: up to five of Genius's nearest results, Statistics' rows with the title (15, `text.primary`) over the artist (13, `text.muted`); a tap loads that page under the same header.
4. Panels **ABOUT** (the write-up), **QUESTIONS & ANSWERS**, **ANNOTATIONS**, **CREDITS**, **CONNECTIONS** and **COMMENTS**, each only when Genius has something for it, in that order. An entry (a question, an annotation, a comment): its first line (15, `text.primary` at `dialog.emphasisWeight`; a lyric line `text.muted`), a note on its right ("Verified"; "Mar 7, 2017 · 297 votes") in 13 `text.muted`, then the text (15, `text.secondary`). Credits and connections: the label in `text.muted` in a `genius.creditLabelWidth` column, the names after it; a connection names five songs, "Title · Artist" one per line, then "and 80 more". COMMENTS has "57 comments" at the right of its header, most-voted first, 50 at a time, and **Show 50 more** at the end ("Loading…" while they load).

**How the song is found** (`GeniusMatch`): searched as "artist title" with the title's extras left off ("(Remastered)", "- 2011 Remaster", "(Live)", "feat. X"), then by the title alone; a result counts only when its artist and its title are the song's, both compared loosely (case, accents, punctuation, "&"/"and", a leading "The"). Genius's own translation pages never count. **Links**: a web address in Genius's text is a link (`text.primary`, `dialog.emphasisWeight`, underlined: the desktop's `theme.link`, since blue is for artist names), opening the browser. **Left out**, as on the desktop: unreviewed annotations, the write-up's own annotation (it is ABOUT), unanswered questions, translation pages. Each song's lookup and page are kept for the run (in memory), so the same song again asks Genius nothing; a failure is never kept.

## 6. Playback

### 6.1 Engine

- **BASS for Android** decodes (with its add-ons for FLAC, DSD, ALAC, APE, WavPack, Opus, Musepack and the rest the desktop plays). AudioFool writes the decoded audio to **its own output stage** (an `AudioTrack` opened at the track's own sample rate and bit depth wherever the route allows), so it decides what reaches the DAC.
- **Gapless**: the next track is decoded and queued before the current one ends, with no gap between album tracks.
- **DSD**: DoP when the output is bit-perfect and the DAC takes it; otherwise converted to PCM (follow the desktop's `DopRule`).
- **Media session** (a foreground media service): lock screen and notification controls with art, headset and Bluetooth buttons, audio focus, and a pause when headphones are unplugged.
- **Plugging in never starts the music** (0.2.3, the user's call): a play from outside the app (a headset or Bluetooth key, the lock screen, the notification) within 3 s after a USB or wired device comes or goes is ignored, and one up to 3 s before it (the key can arrive before Android names the device) is undone with a pause. A USB-C adapter often "presses" play as it connects. The app's own buttons are never held back. `PlugGuard` in `core`; Statistics > Debug's **Plug guard** row counts what it did. **Plugging a USB DAC or headphones in while music plays pauses it** (0.4.4, the user's call: music had moved from the speaker to a just-plugged DAC by itself, loud); the user presses Play when ready. The Bit-Perfect driver's own give-back, which drops the DAC and brings it back, isn't a plug.
- **Resume**: reopening the app restores the queue, track and position, paused (desktop `ReopenPoint`). The whole library shuffled (§4.1) is a queue of every song, so its resume file is a few MB on the M21; it is gathered and written off the main thread.
- **No click at a jump** (0.1.4, the desktop's rule): a seek, a skip or a song tapped while another plays fades the old sound out over 5 ms before it is cut, and a jump into the middle of a song fades in over 5 ms. DoP is never faded.

### 6.2 Bit-Perfect

| Output | What BP does |
|---|---|
| S24 + USB DAC | **On: the app's own USB Audio driver plays to the DAC** (0.4.0 to 0.4.6, `design/usb-bit-perfect.md`), on an Android 14+ phone whose USB mixer offers no bit-perfect entry (the S24 offers none, and no 44.1 kHz). It takes the DAC from Android (USB permission, asked once; "Always open AudioFool" for the DAC makes it at every plug) and sends each track at its own rate in a slot that holds its samples exactly: 16-bit as 16, 24-bit as 24, lossy as 32, DSD as DoP at any rate the DAC takes. Readout "Exclusive". **Volume**: the DAC's own hardware volume, 60 steps of 1 dB below its loudest on the volume keys (the media session's remote volume); the samples are never touched. It comes from the user only: the quietest heard step the first time after the app starts, then where the keys left it (Samsung turns a USB DAC down in its own software and says it takes 0 dB off, so nothing read from Android may decide it: it came in at full volume twice, 0.4.2 and 0.4.3). Muted from the moment the DAC is taken, and at each rate change, until the new stream has settled (no pop). **Giving it back** (BP off, the player stopping, a minute paused, at once when paused and AudioFool leaves the screen (0.4.8), a track it can't play): released, reattached to Android's driver and reset, which Android takes as a replug; Android's media volume is lowered to 1 first and the DAC returned to 0 dB, so Android's path starts quiet and can go all the way up. While the driver holds the DAC, the media service stays in the foreground, paused too, so Android can't end the app before the minute's give-back (the notification can be swiped away again once the DAC is Android's); swiped from recents while paused, it gives the DAC back at once (Samsung ends the app at the swipe, so leaving the screen paused already has). While the driver plays, a silent `AudioTrack` (zeros only) plays too, so Android counts the app as playing and doesn't stop it at an app switch (0.5.1). A DAC still left held when Android ended the app (a crash, a force stop, an update) is given back the same way the next time the app starts (0.4.7). **BP off while playing pauses**; the user turns up and plays on. A DAC pulled out pauses. If the driver can't play a track, the mixer below plays it. **Otherwise (a phone with a bit-perfect mixer)**: the app asks Android for the bit-perfect mixer on the USB device (`AudioManager.setPreferredMixerAttributes` with `MIXER_BEHAVIOR_BIT_PERFECT`, Android 14+), at each track's rate. Where the phone offers no bit-perfect entry at that rate, it sets an ordinary mixer entry at the track's rate instead: no resampling, but still Android's mixer, so the readout says "rate matched", never "bit-perfect" (the user's call, session 4). No entry at the rate at all: shared. A USB device that lists no mixer entries (and that the driver can't play to) greys BP out. |
| M21 headphone out (and a USB DAC on the M21, which has no mixer API on Android 13) | The M21 lists its 3.5 mm and 4.4 mm jacks to Android as the built-in speaker (it has no speaker), so on a FiiO player the speaker route is taken as Headphones (0.1.2). On: the app opens the output at the track's own rate, in whole-number samples, at full volume, and leaves the rest to FiiO's system SRC bypass. The readout says "Bit-Perfect" only when the output is seen running at the track's rate, and "Resampled" otherwise. On a FiiO player the rate is the one FiiO reports its DAC running at (`fiio.intent.action.SAMPLE_RATE_CHANGED`, its `rate`), once it has reported one for the output open now (the user's call, 0.1.5); before that, and on other players, the system's media output (`AudioTrack.getNativeOutputSampleRate`), which on the M21 always says 48 kHz. |
| Bluetooth, phone speaker | Not possible. BP is greyed out (`disabledOpacity`) and can't be tapped. |

The shared output never takes 24-bit packed samples: a 24-bit track goes to Android's mixer as float, which holds it exactly (24-bit packed came out as static on the M21, 0.1.1), and the M21's way sends anything wider than 16-bit as 32-bit. The setting is saved. Off means the normal shared output. Turning it on or off, or a change of route (a DAC plugged in, Bluetooth connecting), reopens the output where the song was heard. On a bit-perfect path the app never turns the volume down: a prompt that would duck the music pauses it instead.

### 6.3 Output readout

One line describing what actually reaches the output, built like the desktop's `OutputReadout`: the output's name, the depth, the rate and a note, with a dot between each (0.2.5, the user's call; the depth before the rate since 0.6.0, the user's call, as in the quality line). Examples: "Shanling UA2 Plus · 24-Bit · 96 kHz · Exclusive", "Shanling UA2 Plus · 24-Bit · 96 kHz · Rate Matched", "Shanling UA2 Plus · 176.4 kHz · DSD over PCM · Exclusive", "4.4mm · 24-Bit · 96 kHz · Exclusive", "3.5mm · 44.1 kHz", "Speaker · 48 kHz · Resampled", "Bluetooth · 48 kHz · Resampled". **The name** (`OutputNames`): a USB device by the name Android gives it ("USB" when it has none of its own); a FiiO player's headphone out by the jack FiiO says is in use, "3.5mm" (its `HEADSET_TYPE_CHANGED` `type` 1) or "4.4mm" (8), remembered across starts since FiiO says only at a plug, **"No Output"** with nothing plugged in (`type` 0; the M21 has no speaker, so nothing is heard: the readout is just those words, 0.2.6, the user's call), and "Headphones" before it has said; any other phone's headphone jack "3.5mm"; else "Speaker", "Bluetooth". **Exclusive** is the bit-perfect note (the desktop's word; "(Bit-Perfect)" until 0.2.5). No "Shared": an output that isn't bit-perfect or rate matched is shared, so the word said nothing; and the words are capitalised (both the user's calls, 0.2.2). The desktop's own readout keeps its "Shared" / "Exclusive". The shared output's depth isn't known to an app, so it is left out; the Bluetooth codec isn't either (it's a system-only API), so there's no "LDAC". Shown under Now Playing's controls and on the Settings row.

### 6.4 BP button

A 34 dp round button labelled "BP" (12/700). The label is `bpLabel.on` when Bit-Perfect is on and `bpLabel.off` when it's off. A tap toggles it, unless it's greyed out (§6.2).

## 7. Last.fm

Scrobbling as on desktop (`LastFmApi`, `LastFmScrobbler`, `PlayTracker`, `ScrobbleQueue`): now-playing updates, scrobbles under Last.fm's rules, and an offline queue. Connect asks for the user's Last.fm username and password (after 0.8.0, the user's call) and sends them once, over HTTPS, to Last.fm's sign-in for phone apps (`auth.getMobileSession`), which gives back a session; the password is kept nowhere. That sign-in needs an app's own API key and secret, so **AudioFool's are built into the app**: they live outside the repo, in `~/.gradle/gradle.properties` on the build PC (`audiofool.lastfm.apiKey`, `audiofool.lastfm.secret`), and a release build stops without them. They are readable by anyone with the APK, which gives no way into anyone's account; the APK goes only to the private repo's releases (private since 0.9.0, so the key isn't published) and the phones; if Last.fm ever suspends the key, a new build with a new key is needed. The session, and the key it was made with, are stored encrypted (Android Keystore), never in the repo; a session made earlier with another key (the desktop's, typed in up to 0.8.0) keeps working with that key. The desktop still connects through the browser. The play is counted from the heard position, so a scrobble's rules (half the song or four minutes, seeks don't count) are the desktop's exactly. Listening History (§4.7) reads the user's totals, top lists and recent plays with the API key alone.

## 8. Library and cache

- The scan walks the chosen folders and reads tags and art. The tag reader must cover every format in the desktop's `AudioFormats`, DSF and DFF included.
- A cache makes a cold start with 26,000 tracks show the library at once. A rescan only reads files whose size or date changed (desktop `FileStamp`, `LibraryCache`).
- Artist, album and song order, release dates, and search follow the desktop's Core rules. Port them, and port their tests.
- A folder that can't be reached (the SD card out) keeps its tracks, shown as unavailable. When the card is ejected, a song on it that is playing stops at once, paused where it was heard (Android ends any app still holding a file open on it), and carries on with the card back (session 5).
- Cover thumbnails are cached on disk and decoded at display size. Scrolling 26,000 tracks must stay smooth on the M21 (Snapdragon 680, 4 GB).
